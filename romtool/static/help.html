How-To: the end-to-end workflow

Step-by-step: floorplan → scale → walls and critical areas → element chain → solve → predict → KPIs → BOM. The math behind every number on this page is documented on the How it works page. An example project ("Example Small Office (LTE)") ships preloaded — on a fresh install it is project id 1; find it any time with GET /projects.

1. Open or create a project

Projects hold floors; floors hold the plan, walls, critical-area polygons and the element chain. Use the project dropdown at the top or + New. Through the API: POST /projects with {"name": "121 Main St"}.

Each project has an environment that selects the indoor path-loss N exponent (office 30 / commercial 22 / residential 28 — editable in config). Default is office; change it with PATCH /projects/{id} {"environment": "commercial"}. A project can also carry a config_overrides dict that deep-merges over the global config (bands, materials, KPI presets, everything else) without touching other projects.

2. Add floors and upload the floorplan image

  1. + Floor prompts for a name and a level number (0 = ground).
  2. Pick a PNG or JPEG under Floorplan image. The image is stored with the floor and the pixel size becomes the prediction grid (w_px x h_px).
  3. Cable runs are graph edges between elements; placing them "on" a floor is bookkeeping only — the chain can span floors (see the example project: riser from SP1 to SP3 feeds floor 2).

3. Calibrate the scale (ppm)

The grid works in pixels; the propagation model needs meters. ppm = pixels per meter. Two ways to set it:

  • Click Calibrate scale, click two points on the plan you know the real distance between (e.g. a 10 m exterior wall), and enter the real distance in meters when prompted. The app sets ppm = pixel distance / real meters.
  • Or type a known ppm value directly in the ppm box.
Scale accuracy directly scales every distance term. On the example project the 12.0 m x 9.2 m plate sits at ppm = 10.

4. Draw walls

  1. Pick a wall material from the Wall material list. Each material carries a tabulated penetration loss in dB at 2 GHz (concrete 15, CMU 10, drywall 4, glass 5, low-E glass 8, wood 4, metal 30 — all editable in config) and its drawing color.
  2. Select the Wall tool and drag on the canvas to draw the wall segment.

Draw the walls that actually block signal paths on this floor: perimeter, shafts, stair cores, glass, metal doors. Wall losses are applied per crossing of the straight line from each antenna to each grid point (same floor only — antennas on other levels use the floor-loss term instead). See How it works → Wall crossings.

5. Mark critical-area polygons

Critical areas are where the NFPA two-tier tier-2 KPI is evaluated:

  1. Select the Critical area tool and click the polygon corners in order.
  2. Close it by clicking near the first corner or press Finish polygon, then give it a label (e.g. "IT room").

Typical uses: fire command center, IT/riser rooms, areas of refuge. The example ground floor carries one ("IT room (critical)", the northwest room). Polygons count at the grid-point level — they do not change the RF; they scope where tier 2 is judged. Edit or add more later: nothing else needs to change.

Area zones

Zones mark parts of a floor that differ, such as a racked warehouse attached to an office. Each zone has a class, which sets its clutter (dB/m) and its default ceiling height band and cable pathway.

  1. Set the class, name, height and pathway in the Zones panel on the left. Pick Zone in the tool palette.
  2. Drag a rectangle over the plan, or click corners and close the shape with Finish polygon or a click on the first corner.
  3. To change a zone, select it with the Select tool. The inspector edits its name, class, height and pathway. Delete zone removes it.

Squares whose centre lies in a zone take the zone's clutter. Later zones win where they overlap. Squares outside every zone keep the automatic clutter map, or the building type when the floor has no clutter map. An antenna inside a zone sits at that zone's ceiling height, which changes its predicted level and autoplace coverage. Zone heights are estimates. Pathways are recorded only.

Building box and perimeter

The Building box tool traces the building outline from the floor plan. Drag a rectangle around the building (leave a margin, keep the title block and sheet border outside), and ROMtool traces the outer walls inside it and draws the outline in cyan. The box is stored with the floor, so a re-trace uses it. If the outline runs along a box edge, the building is cut by the box: enlarge the box. Autoplace keeps antennas inside the outline. Plan import and the trace are also available through the API (POST .../plan, POST .../perimeter/trace).

6. Place the element chain

The cascade is a chain graph: a source feeds a repeater (or feeds the system directly), trunks run to splitters / taps / couplers, branches run to antennas.

  1. Place elements: pick a type in Place element (Source, Repeater, Splitter, Tap, Coupler, Antenna), then click the floor. For antennas pick the type first (omni 2 dBi / panel 7 dBi by default); for splitters pick 2/3/4-way. After placing an element, click it to edit its parameters in the Inspector.
  2. Place cable runs: select the Cable tool, click the feeding element, then the receiving element. The run's length is estimated from the pixel distance and ppm; correct the real length (and cable type) in the Inspector afterwards.

Element parameters (Inspector)

ElementKey fieldsModel meaning
Source (off-air donor)donor_gain_db, feeder_loss_db, optional ambient_dbmOutput = ambient + donor gain - inline feeder loss (per band). Ambients default to the band's config value (-85 dBm across the default set).

Repeater / BDAdl_gain_db, max_dl_out_dbm, ports, optional dl_gain_db_per_bandout = min(in + gain, max out); per-band gain overrides win. Trunk branches limited by ports.

Chain rules the solver enforces: every non-source node takes exactly one cable run in; the source receives nothing; antennas feed nothing; every node must connect back to a source; splitter ways need a configured part (or an il_db override); repeater trunk branches may not exceed its ports. Violations surface as HTTP 422 on solve with explicit messages.

7. Solve the cascade

Solve cascade runs the whole model for every configured band (LTE + FirstNet + LMR + 5G NR by default) and returns a per-band power trace: each node's in/out dBm with the arithmetic in its detail line, each cable run's loss, each antenna's port power, EIRP and cap state. Validation errors (graph problems) are fatal; budget warnings are not: antenna port below 0 dBm, repeater output clamped at max, port power capped. Read these before trusting the heatmap.

8. Predict and read the KPIs

Pick a Band and tick Heatmap. ROMtool predicts every grid point of the floor: each solved antenna contributes its EIRP minus path loss (P.1238 distance and floor terms plus the wall crossings along the straight ray); co-channel contributions combine as a linear (mW) sum. The overlay colors the floor by composite level; the KPI panel on the right shows:

  • Single tier: percent of the floor grid at/above the design threshold (default -95 dBm), pass at 95% by default.
  • NFPA two-tier: Tier 1 (general) = whole floor at/above -95 dBm for 95% of area. Tier 2 (critical area) = inside the critical-area polygons, 99% minimum by default. The tier-2 result combines all polygons as a union (a point in two polygons counts once), with per-polygon rows so you can see which room passed. A floor without polygons falls back to whole-floor tier 2 and says so.
  • SS-RSRP classes (5G NR bands only): bands marked technology: "5G NR" additionally report the floor as a percentage per planning class: excellent (>= -80 dBm), good (>= -90), fair (>= -100), edge (>= -110), none below. These buckets are editable planning defaults, not normative 3GPP classes.
  • Model warnings, e.g. bands predicted below the P.1238 validity window (VHF 150 does) - the number is still printed but flagged as extrapolation.

Grid step: prediction samples the floor every step pixels (1 = full detail). Use step 3-6 for quick sweeps, step 1 for the final number. The full-resolution grid on the example floor is ~11,000 points.

9. Multiband composite view

The composite answers a different question than the single-band heatmap: at each point, what is the best coverage available across a set of bands, and from which band and antenna? It is exposed as an API view plus PNG (no UI control yet): per grid point the strongest band's level, best_band and best_server, and a union KPI counting points where any selected band clears that band's own single-tier threshold. Bands do not combine RF-wise (different carriers are not co-channel) — see How it works → Multiband composite.

10. BOM and exports

Refresh BOM lists parts only (no pricing): cable per type in meters and feet, connectors (2 per run), splitters/taps/couplers by count and way, antennas, sources/repeaters. Export the same bill as CSV or JSON. Critical areas and walls never appear in the BOM.

12. Build the Class 1 labor estimate (Phase 4)

Beyond coverage and parts, ROMtool prices the labor build down the AACE Class 1 stack: catalog unit cards from config/labor_units.json (134 rows, zones A-Rooftop … N-Wrap, O-DC-Power-Plant; regenerate from the owner's CSV with .venv/bin/python scripts/build_labor_units.py) × quantities × access adders × finishing × downtime/logistics × supervision & wrap, with every line visible in the recap. All constants (factor values, ratios, rate card) live in config/estimating.json. REST: POST /estimates computes + stores a definition, POST /estimates/compute is a dry run, GET /estimates / GET /estimates/{id} / DELETE /estimates/{id} manage stored recaps, and the exports render recap.csv / recap.xlsx.

Definition schema (POST body): a name, a non-empty locations[] array, optional top-level extras:

  • Each location: id (unique), name, access — one of ground | ladder | lift | scissor | rope (maps to catalog factors K06 / K03 / K03 / K05; ground = 1.0), conditions[] from occupied | exterior | constrained_access (M03 / M04 / M07), and lines[{catalog_id, qty}] rows from the catalog.
  • schedule: {"night": true/false, "weekend": true/false} (M02 premiums).
  • travel_moves[]: {"from": id, "to": id, "moves": n} — in-venue M05 crew-travel moves between locations.
  • downtime_windows[]: {"label": "...", "days": n} — blacked-out owner/event days; each carries idle crew-day cost, not hours (M01).
  • crew: {"crews", "techs", "foremen", "hours_per_day", "days_per_week"} (defaults from config; 1 crew of 4 techs + 1 foreman, 8 h days, 5-day weeks).
  • Optional per-location power_plant helper: {"runtime_hours": 12, "load_amps": 30, "spill_containment": bool, "battery_monitoring": bool, "rectifier_modules": n?, "string_ah": n?} — auto-derives O01 + rectifiers (N+1: ceil(load/50A)+1) and battery strings (Ah = runtime_hours × load_amps; strings = ceil(Ah / 120 Ah string), IFC 12-hr runtime). Flagged optional: manual O-zone line entry always stays available.
  • Optional rate_overrides: deep-merges over the default rate card per estimate, e.g. {"rate_card": {"tech_rate": 100.0}, "pm_pct": 15.0}.

Reading the recap: per line the factor stack is printed in order — base minutes (qty × unit minutes low/mid/high) → condition (M03/M04/M07) → access (K03/K05/K06) → schedule (M02) → supervision (N01 foreman hours + N02 super hours) → wrap and line-risk contingency (N05, by catalog source-quality P/E/G). Zone rollups, location rollups, crew-days/crew-week stats and the full $ chain (labor → M01 downtime → I05 PM% → overhead → profit → contingency → total) are stacked below the lines. Export renders recap.csv and recap.xlsx from the same data.

Catalog line conventions (read before quoting): FACTOR rows (K03, K05, K06, K14, M02-M04, M07, N01, N02, N05) are multipliers, never line quantities — they are applied via the access/condition/schedule flags and crew plan, and POSTing one in lines[] is rejected. Rows with 0 minutes in DAY/LOT/EA units (A10, B08, H08, I05, J07, M01, K09, K12, O13) are cost-carry quote lines: they carry schedule exposure or recurring service dollars, not field hours — the engine derives the M01 lockout cost from downtime_windows, and the rest belong in the quote. For detail-level estimates the O-DC-POWER-PLANT zone supersedes B05/B06 (48VDC plant + N+1 rectifiers + IFC-sized battery strings instead of the phase-2 placeholders); B05/B06 remain usable for quick ROMs. Heavy reels (>100 lb of 1/2in coax) are handled through the crew plan per K14, not unit minutes.

13. Estimate governance (v0.5.0)

Stored estimates are first-class versioned objects: every write creates an immutable revision, every change lands in an audit log, and the estimate moves through a review state machine before anything leaves the shop. All rules (transitions, frozen states, default owner, binding warn window) live in config/governance.json.

  • Revision history: POST /estimates stores revision 1. PATCH /estimates/{id} with {"definition": {...}, "note": "..."} recomputes, captures a diff summary (lines added/removed/re-priced by stable line ids, changed settings, totals drift) and freezes revision N+1. Revisions are allowed only while the estimate is in draft or review — approved/sent/superseded estimates are frozen and PATCHing them is a 409. Read them back with GET /estimates/{id}/revisions (list + diffs) and GET /estimates/{id}/revisions/{n} (full snapshot).
  • Audit log: GET /estimates/{id}/audit returns every event — actor, action, UTC timestamp, revision and the exact changed paths (lines.bowl-lower:E06.qty, schedule.night, assumptions#12.status, ...). The actor comes from the X-Romtool-Actor header, an ?actor= query param, or the config default (api).
  • State machine: draft → review → approved → sent → superseded via POST /estimates/{id}/state with {"to": "...", "note": "..."}. Legal side steps: review→draft (sent back for re-pricing) and approved→superseded (withdrawn). Every other jump (draft→approved, sent→review, superseded→anything) is rejected with 409 and the allowed list. Deleting is blocked from approved/sent — supersede first. The state and revision are stamped into the recap exports (governance rows in recap.csv, header rows in recap.xlsx).
  • Assumption register: every estimate line whose unit card is an E-grade norm (estimated, not published) auto-populates a register row on create and on every revision — fields: catalog id, line key, assumption text (item + reference), owner (default Senior Project Estimator), review-date, status. Close-out ladder open → verified → closed (verified→open reopens); skipped steps are 409. Re-sync on a revision drops only open rows whose line disappeared — verified/closed rows persist as close-out evidence. GET /estimates/{id}/assumptions + CRUD + POST .../assumptions/{aid}/status; export: GET /exports/estimates/{id}/assumptions.csv.
  • Quote register: POST /estimates/{id}/quotes with vendor, scope, amount, currency, binding_until (ISO date), inclusions[], exclusions[], linked_line_ids[] (estimate line keys like headend:B03) and workflow draft → received → bound → expired (expired→received re-issues). binding_until is inclusive: the price holds through the date and flips to expired the day after (in every read, export and the bid tab — stored status is never silently mutated). Each expired quote warns exactly once in the governance view and in the recap exports; binding windows inside quote_binding_warn_days (14) warn early. lapsed drafts are flagged, never expired.
  • Bid tab: GET /estimates/{id}/bid_tab groups quotes by linked lines (or whole-estimate), ranks them ascending, and reports low/median/high over active received/bound quotes only — drafts are placeholders, expired numbers are stale. The estimate carry per group is wrapped labor + line-risk contingency + idle-cost carry (mid band); whole-estimate quotes are compared against the grand total. Gaps and “carry below the lowest quote” warnings are computed per group.
  • Inclusions/exclusions sheet: the commercial draft generator merges config/commercial_draft.json templates, lines derived from the definition (night/weekend premiums, travel moves, blackout carry, supervision wrap, power-plant sizing), and verbatim vendor-quote terms (active quotes only; expired quotes get an explicit not honored exclusion line). Preview: GET /estimates/{id}/inclusions_exclusions; exports: GET /exports/estimates/{id}/inclusions_exclusions.xlsx (Inclusions_Exclusions + Quotes sheets) and .../inclusions_exclusions.pdf.

14. Commercial wrap constants (v0.6.0)

All commercial constants live in one editable file, config/commercial.json — nothing numeric is hard-coded in the engine. The recap applies them in one documented order (see /how-it-works §11 and the config comment, which carries the order verbatim): direct labor + supervision → downtime idle carry → small-tools/consumables allowance (3% × labor+downtime) → escalation → sales/use tax → insurance/bond carry (1.5%) → PM → overhead → profit (risk tiers low 8 / standard 10 / high 12) → line-risk contingency. Every estimate response carries the applied values in recap.commercial (wrap_order, small_tools_pct, escalation meta, tax classification, insurance pct, profit tier) and the money lines appear in exactly that order.

  • Escalation indices: labor / copper / equipment, each with a base_date and annualized rate. Factor = 1 + days(base_date → anchor)/365 × rate%. The anchor is the definition's commercial.escalation.anchor_date, else the midpoint working day of the with-crews schedule when the definition carries start_date; no anchor → the step is skipped with a warning (never de-escalates).
  • Sales/use tax rules: lines classify by catalog zone prefix via zone_line_types; types in taxable_line_types are taxed at rate_pct (7% editable default, override per estimate with commercial.tax.rate_pct). The shipped default classifies every zone as exempt labor, so the stadium taxes $0.00 — reported explicitly.
  • Overtime: schedule-level double-time flag when planned weekly hours exceed weekly_dt_threshold_hours (40 h); the M02 night/weekend differentials remain the costing mechanism.

15. What-if scenarios (v0.6.0)

Named scenario sets are stored against an estimate and recomputed against the current base at diff time, so they never go stale:

curl -s -X POST $BASE/estimates/1/scenarios -d '{"name": "lift the bowl",
  "overlay": {"access_overrides": {"bowl-lower": "lift"},
              "factor_overrides": {"pm_pct": 12},
              "qty_overrides": [{"location_id": "roof",
                                 "catalog_id": "A09", "qty": 10}],
              "quote_swap": {"quote_id": 3,
                             "line_ids": ["bowl-lower:E06"]}}}'
curl -s $BASE/estimates/1/scenarios
curl -s $BASE/estimates/1/scenarios/1/diff
curl -s -X DELETE $BASE/estimates/1/scenarios/1
  • Overlay families: access_overrides (per-location access method), factor_overrides (deep-merged onto the estimating config), qty_overrides (existing definition lines only), quote_swap (a vendor quote's amount replaces the named lines' wrapped labor, allocated proportionally by each line's share per band; hours/schedule unchanged, swap flows through the full wrap).
  • Diff report: only changed lines (qty / hours mid / labor mid moved) plus the totals delta. The grand-total delta includes the wrap amplification, not the raw labor delta.

16. Bid form export (v0.6.0)

GET /exports/estimates/{id}/bid_form.pdf|.xlsx renders the bid package out of the same engine: base bid (mid band), named alternates[] priced through the identical factor-stack/wrap engine, unit prices per antenna point, a condensed schedule of values in wrap order, the exclusions summary, and a signature block.

  • Alternates live on the definition: "alternates": [{"name": "Alt 1", "locations": ["roof"]}, {"name": "Alt 2", "kind": "deduct", "lines": [{"location_id": "bowl-lower", "catalog_id": "E06", "qty": 5}]}]. locations-only prices that location's whole current scope (including auto-derived power-plant lines); lines specs price a subset (new catalog lines need an explicit qty under kind add); kind deduct prices the removed scope and signs the amount negative (credit when accepted). No travel moves / downtime windows are re-carried inside alternates.
  • Unit prices: base bid ÷ the definition's antenna_points count (scalar or per-location map). Alternates can carry their own antenna_points.
  • Companion endpoints: GET /estimates/{id}/schedule (crew-loading plan, blackout windows, early/late duration bounds, OT flag) and GET /estimates/{id}/cashflow (+ CSV/XLSX exports) from the milestone splits in config/commercial.json.

17. Tips and gotchas

  • Warnings first: a pass/fail on a floor that produced "clamped" or "below 0 dBm budget" warnings is an estimate of a broken chain, not a result.
  • Ambient donor levels are a baseline (-85 dBm); override per source element with ambient_dbm (single number or per band) once you have a site survey number.
  • KPI counts the full floor rectangle including wall pixels - keep that in mind when comparing against a walk-test.
  • Everything numeric (bands, materials, cables, KPI presets, class buckets) lives in config/default.json and can be layered per project via config_overrides.
  • This is a rough-order-of-magnitude tool: empirical models, relative accuracy. It is not a substitute for a site survey or an iBwave-grade prediction.

18. Sanity gates & missing-scope checklists (v0.7.0)

GET /estimates/{id}/sanity runs the rule-driven pre-sign-off checks over the stored recap + definition + quote register. Thresholds and severities live in config/sanity.json; the venue checklists in config/checklists.json. Nothing is hard-coded.

  • Gates: labor share per zone-letter band for the venue archetype (wrapped hours mid share per zone vs a plausibility window), hours → crew-days/weeks consistency (ceil recompute from the stored lines), E-density (share of labor lines on placeholder cards), unit-cost outliers (line unit cost vs the norm-card unit cost — with the default crew plan the ratio equals the line's stacked factor), quote expiry (same date math as the bid tab), and the archetype missing-scope checklist.
  • Hard vs warnings: hard_findings block the approved transition (409 with the findings listed; governance config sanity_blocks_approval). Currently hard: missing-scope checklist items and crew-duration math inconsistencies. Everything else (labor-share bands, E-density, unit-cost outliers, quote expiry) warns only.
  • Archetype: set it on the definition with "sanity": {"archetype": "stadium"} (six shipped: stadium / hospital / warehouse / tunnel / hotel / office), or override read-only with ?archetype=office. With no archetype the labor-share and missing-scope gates report skipped and never block.
  • Checklist math: an entry is satisfied when the estimate carries any labor line whose catalog zone matches the prefix (stadium expects A/C/E/G/H/I/J/K/O); a missing entry is a hard finding naming the zone and the expected scope, e.g. the shipped stadium fixture reports I and J missing until the engineering/electrical rows are added.
  • Exports: recap.csv/.xlsx carry the full sanity section (summary row + every hard/warning finding) under the governance block.

19. Actuals loop: drift & refit proposals (v0.7.0)

Close the norm-card loop with field data. romtool/actuals.py + the estimate_actuals / refit_proposals tables + config/actuals.json; the write-once company layer lives in config/company_labor_overrides.json.

  • Import: POST /estimates/{id}/actuals with {"rows": [{"catalog_id", "location_id"?, "qty", "hours", "cost"?, "date", "note"?}]}. qty/hours > 0, ISO date; one audit event per import.
  • Drift: GET /estimates/{id}/actuals/drift — per catalog card, row ratio = (actual hours / qty) ÷ (effective card mid minutes / 60); the report ratio is the qty-weighted mean, the proposal basis is the qty-weighted median of the row ratios; drift pct and a quality flag (tight ≤ 10%, watch ≤ 25%, else divergent).
  • Propose (never applies): POST /estimates/{id}/actuals/propose-refit scales the card low/high by the median ratio with the ratio clamped into 0.5–2.0 of the current norm (guarded bounds), needs ≥ 2 usable rows, stores the proposal, and never touches the company layer.
  • Apply (owner-approved): POST /estimates/{id}/actuals/apply-refit takes your approved {catalog_id, low, high, note?} and writes config/company_labor_overrides.json (atomic, history appended, audit event on the estimate). The engine prefers the override card on every later compute and stamps company_override provenance on affected recap lines + company_override_catalog_ids. Hand example: E01 (1.8–3.0 min/ft) with rows at median 1.2× proposes 2.16–3.6; a 3.0× median clamps to 2.0× (3.6–6.0).

20. RF link: draft an estimate from the RF project (v0.7.0)

POST /projects/{id}/draft-estimate walks the RF model (floors, antennas, cable runs, splitters/taps, source/repeater, critical areas, solved bands — every mapping in the editable config/rflink.json) and drafts a full estimate definition for estimator review:

  • antenna point counts per floor → E06 lines + definition antenna_points (bid unit prices) + H02 PIM per antenna;
  • cable_run lengths per size → coax footage E01 horizontal / E02 cross-floor riser (run owned by its from-element's floor) + E10 riser fire wrap + E03 both-end connectors + E04 jumpers + D05 supports proportional to footage;
  • splitter/coupler/tapper floors → hub closets (C01/C02/C06/C07) + E05 splitter installs;
  • source/repeater floors → the headend (B-zone, donor-side A-zone, J-zone power feed) plus the booster DC load block → the estimate engine's O-zone auto-sizer (10 A / 12 h config → O01 x1, O02 x2 N+1, O04 x1 string);
  • L-zone allowances: 4 ceiling tiles per antenna point, patch rows per penetration count (A04/C07/D06/D07); H-zone testing per floor × solved band (H04 benchmark, H05 acceptance), H01 sweep per run, H09 carrier acceptance, H06/H07/H10, I-zone engineering.

The default response is a review draft (not stored). Re-POST with ?store=true to compute it and store a real estimate (revision 1, state draft) the estimator then edits via PATCH /estimates/{id}. A test builds it from the seeded example project and asserts every drafted catalog id exists.

21. AI endpoints (v0.7.0)

All three AI endpoints are gateway-agnostic OpenAI-chat-style completions, configured in config/ai.json (base_url, model, api_key_env, prompts). They degrade gracefully:

HTTP 503 {"detail": "ai gateway unreachable", "schema": {..documented request/response shape..}}

when the config file is missing, the key env var is unset, or the gateway is unreachable/non-200; 502 with the same schema when the gateway answers but the body does not fit the contract. No test may call paid APIs — the transport is mocked in tests.

  • POST /ai/rfp-scan {"text": "..."} → requirements / scope matrix / gaps / assumptions (strict JSON).
  • POST /ai/scenario-suggest with {"recap": {...}} or {"estimate_id": n} → suggested what-if overlays with rationale; suggestion overlays are validated against the stored estimate (invalid overlay → 422).
  • POST /ai/bid-memo with {"recap": {...}} or {"estimate_id": n} → narrative memo + highlights; the estimate's assumption register is included in the prompt automatically.
